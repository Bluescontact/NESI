## Candidate 1 — an unresolved fork gets named and queued, never guessed at provisionally

**Source:** `PROTOCOLS.md`, Mandate body: *"A genuine unresolved fork — one a
seat cannot mark LAWFUL-NOW without deciding something that is his — gets
opened as a durable gate... It waits there... until he closes it. It is
never defaulted, never guessed at 'provisionally,' never built around by
picking the answer that keeps the session moving. Queued, not decided."*

**The nutrient, apart from its apparatus:** the specific mechanism (`python
tools/gates.py open --gate ...`) retires with the Mandate. The practice
underneath it — that a real fork gets *named as a fork* and held open,
rather than resolved by whichever answer lets the session keep moving —
does not need that mechanism to be worth keeping. This session's own
completion-condition table (the A-E categories, held across the VE24 and
DREAMDEV work) is this same practice, applied without any Mandate invoking
it.

## Candidate 2 — progress is measured by forks surfaced cleanly, not by output shipped

**Source:** *"Progress under this mandate is measured by LAWFUL-NOW ground
covered and NEEDS-KEVIN gates opened cleanly, never by features shipped."*

**The nutrient:** a session that ships a lot while quietly resolving forks
it had no authority to resolve did worse than a session that ships little
and surfaces every fork it hit. This is a real, checkable standard for
self-assessment independent of any specific gate mechanism — "did I name
every fork I couldn't lawfully close" rather than "how much did I build."

## Candidate 3 — a standing pre-authorization is a licence with a date, not a permanent fact

**Source:** *"A LAWFUL-NOW tag is spent with the date it was issued written
beside it... It is a licence with a date on it, not a standing fact."*

**The nutrient:** any prior go-ahead (a mark, an authorization, a mandate
itself) should be readable with its own issue date attached wherever it's
invoked, so a reader can tell whether it's being cited as current permission
or as a stale one. This Mandate's own retirement is itself an instance of
the pattern this candidate names — it took 16 days from issue (2026-08-11)
to this mark noticing the ground had shifted under it (`lens-panel`'s
2026-08-27 authorization).

## Candidate 4 — the falsifier: shipped behavior that only makes sense as a resolved fork means the fork was resolved silently

**Source:** *"If a build ever ships behavior that only makes sense as the
resolution of an open fork... this mandate was breached regardless of how
much progress it produced."*

**The nutrient:** this is a concrete, checkable test — read what actually
shipped, and ask whether it could only exist if some open question had
already been answered one particular way. If so, that answer was made
somewhere, by someone, without being named as a decision. This test
generalizes past this specific Mandate; it's a way to audit any build
session's output for silent fork-resolution, not just counsel-built ones.

## Candidate 5 — a reading and a ruling are different acts, and only one needs to be logged by name

**Source:** the NESI.exe amendment: *"no individual counsel agent's own
definition file was changed — each... still carries 'never defaults his
forks' as its own hard limit... They remain lens-readers under this
amendment; the session converges their reads into a ruling and logs it."*

**The nutrient:** a lens producing a read is not the same act as a session
converging several reads into an actual ruling — conflating them lets a
ruling hide inside what looks like "just gathering input." Keeping them
distinct, and logging the convergence step by name (this Mandate used
`BUILD_RECORD.md`; any durable, checkable location would serve the same
function), is what keeps a multi-lens process from becoming a way to launder
a decision through five voices instead of naming who actually made the call.

## Candidate 6 — a corpus-shaping fork gets asked as a labeled choice, not inferred from momentum

**Source:** *"Put to him directly (AskUserQuestion, same session), because
the answer changes which of two very different corpora this becomes."*

**The nutrient:** the Mandate itself recognized a distinction worth keeping —
some forks are build details (pick one, move on) and some are corpus-shaping
(the answer determines what kind of project this becomes going forward).
The second kind gets asked as an explicit, labeled choice, in the moment,
rather than settled by whichever direction the session happens to already be
moving in.
