Phase 1

The deposit repo: archive, scaffold, first pipeline.

Kevin named an existing private repo, Bluescontact/NESI, already at that name — one commit, a README, 82K total. Rather than pick a different name or delete it, the plan was to archive it whole, then reuse it. Cloned in full (history included, not a snapshot) to nesi_repo_archive_2026-08-30/, still on disk, untouched since.

Scaffold v1 — wholesale copy

First pass: game/ = all of nesi/game2d, knowledge/ = all of nesi/mind. Simple, but not what "deposit" turned out to mean.

The pipeline, named

Kevin: "phase transition, metachrysalis/mycelium colonization process through pattern, and recognition capacity." Translated to filesystem terms: recognition = the gate's real admission ledger (MARKS.jsonl), not a session's own say-so.

tools/build_deposit.js v1

Three buckets, derived every run, never hand-sorted: game (traced from what index.html actually <script src>'s — turned out to be just index.html + solid.js), patterns (anything with a real gate admission), compost (everything else, kept whole).

A real bug, found and fixed

The "at" paths in MARKS.jsonl are relative to gate/ (where admit.mjs runs), not to game2d/ root. First version resolved them wrong — day_one.html and all three session-bridge files were silently landing in compost despite being genuinely admitted. Fixed by resolving against path.join(GAME2D,'gate') instead.

Verified, not assumed

Opened game/index.html from the deposit folder directly in the browser pane — confirmed it rendered correctly standalone, twice, before treating the game bucket as done.

Pushed

Force-pushed to Bluescontact/NESI (unrelated history to the old README-only commit, exactly why the archive step existed). GitHub Pages requested — blocked: Pages needs a public repo on this plan, and the repo was private with real compost in it. Held there rather than making it public with compost still inside.

Phase 3

Reviewed every command run this session: no rm -rf, no git clean/reset --hard against the repo root, every rmrf() in the pipeline scoped to nesi_deposit/ subfolders only. Nothing this session did explained a blast radius that large.

Investigated, not panicked

Checked the Windows Recycle Bin (228 items, none matching), checked for a renamed sibling folder on the Desktop, checked the OneDrive process was running.
