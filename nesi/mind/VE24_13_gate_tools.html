What this edge is, and — first — what it is not

Three systems in this corpus are named "gate" or "ledger." This edge covers exactly one.

Edge 13 sits between Group D (gate/ledger/marks) and Group G (tools/checks). session-derived scope note, carried directly from this edge's own preflight manifest: this file covers only nesi/game2d/gate/ — the live, wired, JavaScript gate that appends to LEDGER.jsonl and runs as one row of check_all.js. It does not cover root gate/gate.py (a separate, Python, "stages and displays, never closes" codebase — read at header level only, see the disambiguation table below) or nesi/nesi_bench_v0/gate.py + ledger.py (a third pair — this edge left it unread, but edge 15 (VE24_15_gate_library.html) has since read both files in full and resolved the disposition; see the table row below and the Related Edges card in the Sources tab).

Read this before anything else on this page. A reader who has seen only one "gate" in this corpus will default to assuming there's one gate system. There are at least three, sharing a name because they were each built to hold a refusal discipline, not because they are the same tool or the same file tree. Confusing them is the single most likely misreading of this whole edge.

Domain D

nesi/game2d/gate/ — builder jurisdiction, five refusals and one admission.

Read in full this pass: gate.mjs, lib.mjs, and all 8 files in gate/instruments/.

gate.mjs — the runner

verbatim, gate.mjs:1-18: "Five mechanisms that refuse rather than advise, and one that admits... Exit 0 if every ACTIVE instrument examined something and passed. Exit 1 on refusal. Exit 3 if an active instrument examined nothing... Jurisdiction: BUILDER'S GATE, not player's surface. Every run is appended to the builder ledger with its grounds. No gate event has a player projection."

Domain G

nesi/game2d/tools/check_all.js — one front door, and where "eight" is not the same count as "twelve."

Read in full this pass (re-read for this edge's specific angle, having also been read for edges 3/21).

Why check_all.js exists

verbatim, check_all.js:4-12: "I ran the store guard, it threw 'window is not defined', I piped it through tail -2, read the last line, and committed. The crash looked exactly like output... So there is one front door. It runs every node instrument, prints one row each, and exits non-zero if ANY of them fails — including by crashing, which is reported as CRASH rather than folded into FAIL."

gate.mjs is genuinely invoked — confirmed, not just named in a comment

instrument fact: check_all.js:151-153 declares const GATE = [["gate", "gate/gate.mjs", "what the build made possible..."]]. That entry is then executed, not merely referenced: check_all.js:238-265 loops over GATE and runs execFileSync(process.execPath, [path.join(HERE, "..", rel)], { stdio: "pipe", cwd: path.join(HERE, "..") }) — a real child-process spawn of gate/gate.mjs, with its stdout/stderr captured, ANSI-stripped, and its exit code read to decide the row's mark (ok / CRASH / THIN / FAIL). This resolves preflight item 1 directly: the invocation is a real subprocess call at a fixed line range, not a comment or a dead reference.

check_all.js's own comment on why the gate gets one row, not many

verbatim, check_all.js:128-150: "It is not in tools/ and it is not one more instrument. It is a second jurisdiction with its own runner, its own ledger and its own verdict grammar, sited at ../gate/. It gets a row here so the build has ONE front door rather than two... The gate's output is relayed verbatim, never re-judged here."
